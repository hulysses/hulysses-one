O que você vai demonstrar

REST

Cadastrar/consultar um parceiro e validar um fornecedor remotamente para criar um produto.

Mensageria

Cadastrar agora e registrar a atividade depois, inclusive com o consumer temporariamente parado.

Batch

Ler um CSV, processar os registros e persistir em chunks de 10.

BusinessPartner, atividades e Batch pertencem ao business-partner-service. Produtos e pedidos pertencem ao hulysses-app. O consumer usa a mesma imagem e o mesmo banco do domínio de parceiros.

Antes de começar: use a mesma janela do PowerShell nos testes manuais para preservar $partner, $product e $queuedPartner. Os endereços abaixo consideram as portas padrão de .env.example.

01Preparar e subir o Compose

  1. Abra o Docker Desktop e aguarde o engine de containers Linux iniciar.
  2. Abra o PowerShell na raiz do projeto.
  3. Crie .env somente se ainda não existir.
Set-Location 'C:\Users\hulys\Documents\hulysses-one'
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
notepad .env

Preencha DB_PASSWORD, PARTNER_DB_PASSWORD e RABBITMQ_PASSWORD. Se já houver .env, acrescente as opções RabbitMQ de .env.example preservando as credenciais atuais.

Alterar a senha no arquivo não altera automaticamente usuários de bancos ou broker com volumes já inicializados. Use as credenciais atuais. Não apague volumes para executar este roteiro.

Execute os comandos abaixo um por vez, avançando somente se o anterior terminar com sucesso. A primeira construção pode levar alguns minutos.

docker compose config --quiet
docker compose up -d --build --wait --wait-timeout 240
docker compose ps -a

Esperado: sete serviços healthy: config-server, hulysses-db, business-partner-db, rabbitmq, business-partner-service, business-partner-consumer e hulysses-app.

03Cadastrar parceiro e produto via REST

Antes do POST, abra RabbitMQ Management → Exchanges → business-partner.events e, em outra aba, Queues and Streams → business-partner.activities. Confirme que a fila tem um consumer.

A. Criar parceiro pela API principal

O documento aleatório tem 11 dígitos, compatível com INDIVIDUAL, e reduz conflitos ao repetir a demonstração. A validação acadêmica verifica formato/tamanho; não verifica dígitos de CPF.

$document = '3' + (Get-Random -Minimum 1000000000 -Maximum 9999999999).ToString()
$partnerBody = @{
  name = 'Parceiro Demo'; document = $document
  email = 'demo@example.com'; phone = '11999990000'
  type = 'INDIVIDUAL'; roles = @('CUSTOMER', 'SUPPLIER')
} | ConvertTo-Json
$partner = Invoke-RestMethod 'http://localhost:8080/business-partners' `
  -Method Post -ContentType 'application/json' -Body $partnerBody
$partner
Invoke-RestMethod "http://localhost:8081/business-partners/$($partner.id)"
Invoke-RestMethod "http://localhost:8081/business-partners/$($partner.id)/eligibility?role=SUPPLIER"

Esperado: cadastro 201, ID retornado e consultas 200. O cadastro em 8080 é encaminhado por Feign ao serviço de parceiros; o dado pertence ao banco de parceiros.

B. Criar produto usando o fornecedor remoto

$productBody = @{
  name = 'Produto Demo'; description = 'Integracao REST'
  price = 10.50; supplierId = $partner.id
} | ConvertTo-Json
$product = Invoke-RestMethod 'http://localhost:8080/products' `
  -Method Post -ContentType 'application/json' -Body $productBody
$product
$product.supplier.id
Invoke-RestMethod 'http://localhost:8080/sales-orders/total'

Esperado: produto 201 com supplier.id igual ao parceiro; total de vendas 200. Produtos são persistidos no PostgreSQL do principal.

Restaure a API antes de continuar. Este cenário é diferente de parar apenas o consumer na etapa 05.

04Ver publicação, consumo e histórico

O POST anterior já gerou um evento. Confira os logs do producer e do consumer:

docker compose logs --tail 80 business-partner-service business-partner-consumer
$activities = Invoke-RestMethod "http://localhost:8081/business-partners/$($partner.id)/activities"
$activities | ConvertTo-Json -Depth 5
  1. Producer: procure Published BUSINESS_PARTNER_CREATED.
  2. Consumer: procure Processed BUSINESS_PARTNER_CREATED.
  3. Compare eventId e businessPartnerId nos logs e no histórico.
  4. No histórico, confirme occurredAt e processedAt. Se estiver vazio, aguarde alguns segundos e repita a consulta.
  5. Na Management UI, observe publicação no exchange e entrega/ACK na fila. Métricas podem levar alguns segundos para atualizar.
Fila vazia é normal com consumer ativo. A mensagem pode ser consumida antes de você abrir a tela. Logs e histórico comprovam o processamento; o próximo cenário permite inspecionar o JSON aguardando.

A mensagem leva identificadores e informações do evento, sem repetir dados pessoais do cadastro:

{
  "eventId": "1bb2ed22-8f8d-4b6e-83ef-89459b1b56b2",
  "eventType": "BUSINESS_PARTNER_CREATED",
  "businessPartnerId": 10,
  "occurredAt": "2026-10-05T20:30:00Z"
}

JSON ilustrativo; IDs/horários reais serão os do seu cadastro. Publicação após commit, ACK após gravar a atividade e eventId para evitar duplicidade na reentrega.

05Demonstrar consumer indisponível

A. Parar somente o consumer e cadastrar outro parceiro

Mantenha API, PostgreSQL e RabbitMQ ligados. Use outro documento e guarde o novo ID em $queuedPartner.

docker compose stop business-partner-consumer
$queuedDocument = '4' + (Get-Random -Minimum 1000000000 -Maximum 9999999999).ToString()
$queuedBody = @{
  name = 'Parceiro Aguardando'; document = $queuedDocument
  email = 'aguardando@example.com'; phone = '11999990001'
  type = 'INDIVIDUAL'; roles = @('CUSTOMER')
} | ConvertTo-Json
$queuedPartner = Invoke-RestMethod 'http://localhost:8080/business-partners' `
  -Method Post -ContentType 'application/json' -Body $queuedBody
$queuedPartner
$queuedHistory = Invoke-RestMethod "http://localhost:8081/business-partners/$($queuedPartner.id)/activities"
@($queuedHistory).Count

Esperado: cadastro 201, mesmo com consumer parado. Histórico do novo parceiro com 0 atividades.

B. Inspecionar a mensagem aguardando

  1. Management → Queues and Streams → business-partner.activities.
  2. Confirme Consumers = 0 e Ready ≥ 1.
  3. Expanda Get messages; escolha ACK com requeue habilitado e solicite uma mensagem.
  4. Confira o JSON e o ID de $queuedPartner. Se houver mensagens anteriores, inspecione mais mensagens mantendo requeue.
  5. Confirme que a mensagem continua na fila após a inspeção.
Não use ACK com remoção nem “Purge”. A mensagem precisa permanecer na fila para a retomada. Este teste demonstra consumer indisponível, com broker disponível. Se o broker falhar durante a publicação, a implementação registra a falha no log e não recupera essa mensagem automaticamente.

C. Retomar o consumer e verificar o consumo

docker compose start business-partner-consumer
docker compose ps -a
docker compose logs --tail 80 business-partner-consumer
$queuedHistory = Invoke-RestMethod "http://localhost:8081/business-partners/$($queuedPartner.id)/activities"
$queuedHistory | ConvertTo-Json -Depth 5

Aguarde o consumer reconectar e repita logs/consulta se necessário. Esperado: consumer ativo, fila sem mensagens pendentes após processar tudo e uma atividade para o novo parceiro. A requisição original já tinha concluído antes dessa atividade.

Opcional: persistência da fila ao reiniciar RabbitMQ

Execute entre B e C, mantendo o consumer parado. Aguarde RabbitMQ saudável e confirme a mensagem Ready na Management UI; depois faça C.

docker compose restart rabbitmq
docker compose ps -a

Não apague o volume.

06Importar CSV com Spring Batch

Abra o CSV de exemplo: 13 registros, sendo 12 válidos e 1 inválido. O cabeçalho deve ser exatamente:

name,document,email,phone,type,roles
Agro Parana,11000000000101,contato@agroparana.example,41999990001,COMPANY,SUPPLIER
Joao da Silva,11000000001,joao@example.com,41999990002,INDIVIDUAL,CUSTOMER
Cooperativa Oeste,11000000000102,contato@coop.example,41999990003,COMPANY,CUSTOMER;SUPPLIER

type é INDIVIDUAL/COMPANY. CUSTOMER/SUPPLIER são roles, separados por ponto e vírgula quando houver mais de um. Este é um trecho; use o arquivo completo para conferir os contadores.

Job: businessPartnerImportJob
Step: businessPartnerImportStep
FlatFileItemReader → processor → writer → BusinessPartnerService.create
Chunks de 10 · persistência existente · metadados BATCH_* no PostgreSQL

A. Executar o exemplo incorporado no JAR

$batchResult = Invoke-RestMethod 'http://localhost:8081/batch/business-partners/import' -Method Post
$batchResult | Format-List
docker compose logs --tail 150 business-partner-service

Se os documentos do CSV ainda não existirem, o resultado deve ser status = COMPLETED:

13readCount · lidos
12writeCount · gravados
1filterCount · filtrados
2commitCount · commits

Procure nos logs Business partner import chunk processed: written=10 chunkSize=10 e depois written=2. O processor normaliza strings/documentos/enums e reutiliza validações; o inválido é filtrado. O writer chama o service existente em cada chunk.

B. Consultar os registros persistidos

$allPartners = Invoke-RestMethod 'http://localhost:8081/business-partners'
$importedPartners = @($allPartners | Where-Object { $_.document -like '110000000*' })
$importedPartners | Select-Object id, name, document, type, roles
$importedPartners.Count
docker compose logs --tail 80 business-partner-consumer

Esperado: os 12 documentos válidos aparecem no banco; o inválido não foi cadastrado. O Batch também publica eventos e o consumer cria atividades. Se já havia esses documentos, confira nomes/IDs e os contadores da execução.

C. Demonstrar upload e reimportação

O mesmo endpoint aceita multipart com campo file. Como A já importou o exemplo, repetir abaixo deve resultar em COMPLETED, writeCount=0 e filterCount=13, sem duplicar parceiros.

curl.exe -X POST 'http://localhost:8081/batch/business-partners/import' `
  -F 'file=@business-partner-service/src/main/resources/batch/business-partners.csv'

Para gravar novos registros por upload, copie o CSV para outro arquivo, informe documentos novos válidos e ajuste file=@.... Use curl.exe: curl pode ser alias do PowerShell.

Confira status, não apenas o HTTP. Cabeçalho/estrutura incorretos podem retornar HTTP 200 com FAILED. O chunk com falha é revertido, mas commits anteriores permanecem. Cada chamada cria uma execução nova; não há restart automático ou scheduler.

Se já importou, writeCount pode ser menor ou zero. Use documentos novos para demonstrar novas gravações; não precisa limpar o banco. O endpoint aguarda o resultado, mas o pipeline usa Job, Step e chunks do Spring Batch.

07Conferir bancos, metadados e volumes

Com usuários/bancos/schemas padrão, consulte diretamente. Se personalizou o .env, ajuste os argumentos:

docker compose exec -T hulysses-db psql -U hulysses -d hulysses `
  -c 'SELECT id, name, supplier_id FROM public.product;'
docker compose exec -T business-partner-db psql -U business_partner -d business_partner `
  -c 'SELECT id, name, document FROM business_partner_service.business_partner ORDER BY id;'
docker compose exec -T business-partner-db psql -U business_partner -d business_partner `
  -c 'SELECT business_partner_id, event_type, processed_at FROM business_partner_service.business_partner_activity ORDER BY processed_at;'
docker compose exec -T business-partner-db psql -U business_partner -d business_partner `
  -c 'SELECT job_execution_id, status FROM public.batch_job_execution ORDER BY job_execution_id;'
docker compose exec -T business-partner-db psql -U business_partner -d business_partner `
  -c 'SELECT job_execution_id, read_count, write_count, filter_count, commit_count FROM public.batch_step_execution ORDER BY step_execution_id;'

Esperado: produto no banco principal; parceiros/atividades no banco do domínio; execuções/contadores Batch no schema public desse mesmo banco.

Problemas frequentes

SintomaO que conferir
Compose exige senhaPreencha as três senhas no .env. Não o versione.
Container encerra ou fica sem saúdedocker compose logs --tail 120 NOME_DO_SERVICE. Corrija a causa antes de avançar.
Principal tenta localhost:5432Recrie o principal com o Compose atualizado. Ele usa hulysses-db por padrão e ignora a variável local DB_URL. Confira um eventual override DOCKER_DB_URL.
role "hulysses" does not existO volume pode ter sido criado com outro usuário. Ajuste DB_USERNAME no .env para o usuário existente (por exemplo, postgres), preservando a senha válida e o volume.
Documento já cadastradoGere outro documento. Batch filtra duplicados; nova gravação exige documentos novos.
Fila vaziaCom consumer ativo, é esperado. Para ver mensagem aguardando, faça o cenário 05.
Consumers maior que zero após stopPode haver listener local em dev ou outro consumer ligado. Pause-os e confira o broker/porta corretos.
Histórico vazio após startAguarde reconexão, consulte logs e confira Ready, credenciais e ID correto.
Batch retorna FAILEDConfira cabeçalho/estrutura CSV e logs. HTTP 200 sozinho não prova sucesso do Job.
Senha nova falha na autenticaçãoVolumes inicializados mantêm usuários anteriores. Restaure credenciais válidas ou atualize o usuário conscientemente; não apague dados.
Corrigir URL antiga do banco principal no Docker

O Compose usa hulysses-db e DB_NAME por padrão. A variável DB_URL é reservada ao desenvolvimento local. Se precisar personalizar a conexão Docker, use DOCKER_DB_URL no .env com o hostname do serviço. DB_USERNAME deve corresponder ao usuário do volume existente; alterar esse valor não cria outro usuário no banco. Limpe eventuais overrides antigos da sessão antes de recriar o principal.

Remove-Item Env:DOCKER_DB_URL, Env:DB_USERNAME -ErrorAction SilentlyContinue
docker compose up -d --force-recreate --wait --wait-timeout 240 hulysses-app
docker compose logs --tail 80 hulysses-app

Demais hostnames: business-partner-db, config-server, rabbitmq. O erro Hibernate de Dialect pode ser consequência da conexão recusada; corrija a conexão indicada no log.
